# 工地日记 Worksite Diary

[English](./README.md)

一个用于记录每日工地情况的简单 iOS App —— 作为云端作品集项目的实践之作，涵盖移动端开发、Postgres 后端，以及配套的网页管理后台。

## 功能特性

- 首次启动时会有一个简短的新手引导，介绍应用的主要功能
- 邮箱 + 密码登录（Supabase Auth），每个用户只能看到自己的记录
- 记录每日条目：工地名称（自动联想最近使用过的工地）、日期、上下班时间（原生选择器）、备注、任务（预设选项快速勾选或自由填写），以及工地的 GPS 定位——自动反查为易读的具体地址
- 从相册选择照片，或直接用相机拍摄；点击照片可全屏查看，支持双指缩放或双击放大，滑动可瞬间切换到上一张/下一张
- 同样支持添加视频（相册选择或现场拍摄；拍摄时长上限 45 秒、中等画质，上传体积上限 45MB，以便稳妥地控制在 Supabase 免费套餐 50MB 的上限以内），应用内自带原生控件播放；视频缩略图显示的是一个播放图标，而不是真实的视频帧画面，这样可以避免为了生成预览图而重复下载视频数据
- 一键复制条目，快速新建一条预填了工地、任务、备注的记录
- 保存后可随时编辑或删除条目
- 可在列表视图和照片网格视图之间切换浏览，支持按工地或任务搜索，还可通过顶部的日历选择器直接跳转到指定日期
- 工时统计——按本周或本月汇总总工时，并按工地拆分明细
- 支持离线使用：在没有网络（或网络太差以至于无法真正完成上传）的情况下新建、编辑或删除条目会先保存在本地队列中，联网后自动同步，同步完成前会显示待同步标记
- 将某条记录导出为 A4 尺寸的 PDF，并通过 iOS 原生分享菜单分享给任何人
- 独立的网页管理后台，可查看和编辑所有用户的记录

## 这些功能背后的考虑

其中几个功能是专门针对工地实际使用场景来做优先级排序的，而不只是常规的增删改查打磨：

- **工地名称自动联想** —— 同一个班组往往会在同一个工地连续工作好几天甚至几周，每天都重新打一遍工地名称是可以省掉的麻烦。
- **一键复制条目** —— "和昨天同一个工地"是很常见的情况。用上一条记录预填新条目可以省去重复输入；日期、时间、照片会留空，因为这些是每天都不一样的信息。
- **工时统计** —— 按工地、按周汇总工时，本质上就是一份工时报表，而这些数据每条记录本来就已经在记录了——只是缺一个汇总和展示的页面。
- **离线优先的写入** —— 工地经常信号不好甚至完全没有信号。如果没有这个功能，没网络时保存条目会直接失败。把写入操作先存在本地、联网后自动同步，是直接针对这个实际使用场景做的处理，而不只是当作一个边缘情况顺带处理。

## 技术栈

- [React Native](https://reactnative.dev/) + [Expo](https://expo.dev/)（SDK 54）+ TypeScript
- [Expo Router](https://docs.expo.dev/router/introduction/) 实现基于文件的路由导航
- [Supabase](https://supabase.com/)（Postgres + Auth + Storage）作为后端 —— 客户端直接访问，通过行级安全策略（RLS）保护数据
- 离线优先的写入机制：本地队列（[`@react-native-async-storage/async-storage`](https://react-native-async-storage.github.io/async-storage/)），联网后通过 [`@react-native-community/netinfo`](https://github.com/react-native-netinfo/react-native-netinfo) 自动同步
- [`expo-video`](https://docs.expo.dev/versions/latest/sdk/video/) 用于应用内视频播放
- [EAS Build](https://docs.expo.dev/build/introduction/) 用于编译和签名 iOS 安装包

## 快速开始

1. `npm install`
2. 创建一个 [Supabase](https://supabase.com/) 项目
3. 在 Supabase 的 SQL Editor 中，**按顺序**运行 `supabase/` 目录下的文件：`schema.sql`、`002_admin_panel.sql`、`003_comments_and_location.sql`、`004_address.sql`、`005_videos.sql`
4. 将 `.env.local.example` 复制为 `.env.local`，填入你的 Supabase 项目 URL 和 anon/publishable key（在 Project Settings → API 中获取）
5. 运行 `npx expo start`，用 Expo Go 打开；或运行 `npx expo run:ios` 在已连接的设备上进行独立构建

## 离线支持

新建、编辑、删除条目在没有网络时也能正常使用。改动会先保存在本地队列中——新建的条目会当场生成好本地 ID，同步后无需再做任何 ID 对应处理——联网后会自动同步到 Supabase；尚未同步的条目会在列表、网格和详情页显示一个小的待同步标记。

这里仅覆盖“写入”场景：浏览记录首次加载时仍需要网络连接，本应用不会缓存已加载过的数据以支持完全离线浏览。对一条已同步条目做的离线编辑会被安全地放入队列，但在同步完成前，该条目自己的详情页不会显示这次修改；只有全新的离线新建条目会完全基于本地数据正常显示。

保存时不会仅凭上传调用没有报错就认为照片或视频已经传成功——之后还会向存储服务确认一遍，因为在网络不稳定时，上传请求有可能在文件并未完整传输的情况下依然"正常返回"。如果这项确认失败，保存会自动回退到同一套离线队列机制，而不是直接报错失败——这样一条记录只会因为真的离线而进入排队等待同步，不会因为网络不稳定就丢失。视频文件体积天然更大，所以这一点对视频比对照片更重要。

在完全没有网络的情况下打开 App，现在也能正常打开并保持登录状态——具体原因见下面的改进记录。

## 改进记录：在完全没有网络的情况下也能打开 App

App 的登录状态本来就存在本地存储里，这从来都不是问题所在——真正的原因更具体一些。Supabase 的 `getSession()` 调用，每次都会先检查访问令牌是不是快要过期或者已经过期，如果是，就会先在背后发一次刷新令牌的网络请求——由于令牌有效期大约只有一小时，几乎每次"冷启动"（比如隔了一天再打开 App）都会触发这个检查。这个刷新是一次真实的网络请求，在完全没有网络的情况下，它会按退避策略反复重试，最长能卡住将近 30 秒——而这段时间屏幕上只有一个光秃秃的转圈动画，既没有超时机制，也没有做离线检测，更没有任何兜底方案。这就是为什么它看起来像是"完全打不开"，而不只是"有点慢"：现在会先用 `NetInfo`（离线写入队列那里已经在用的同一套机制）检查一下网络状态，如果没有网络，就直接从本地存储里读取已保存的登录状态，而不再走那次刷新请求——这样 App 能立刻打开，直接用上次缓存的登录状态。等下次联网后，正常的令牌刷新还是会照常进行。

## 调试记录：快速保存后照片丢失的问题

这个问题值得记录一下，因为花了好几轮才真正找到根因：保存一条记录（尤其是带多张照片、或者刚选完照片就立刻保存）有时会"成功"跳转离开，但照片其实没有被保存进去——没有任何报错或提示，就是单纯地丢了。排查过程中走过几次弯路，最后才定位到真正的原因：

1. **第一个猜测：上传本身不稳定。** Supabase 的存储上传接口 `upload()` 在网络不好的情况下，有可能在文件并未完整传输的情况下依然返回"没有报错"。于是加了一个上传后的确认步骤（用 `HEAD` 请求检查文件是否存在、`content-length` 是否匹配），确认失败就回退到离线队列。结果并没有解决这个已报告的问题。
2. **确认了这个改动不会影响离线支持。** 顺着离线逻辑走了一遍，确认真正离线时会直接跳过上传（提前就检测到了）、正常进入队列；同时把"网络不稳定导致确认失败"的情况也归并到同一套离线队列里，而不是直接报错。问题依然存在。
3. **第二个猜测：保存过程中被中途导航离开。** Save/Cancel 按钮在保存中会被禁用，但这挡不住 iOS 的边缘右滑返回手势，也挡不住 Android 的物理返回键，这两者都能绕过屏幕上按钮的禁用状态。于是在保存进行中显式屏蔽了手势返回和物理返回键，并在保存按钮上加了加载动画，避免多张照片上传较慢时看起来像卡住了。用户测试后反馈问题依旧存在。
4. **这次拿到了真正有用的排查信息。** 询问了保存时有没有弹出"已离线保存"的提示（没有），以及这次测试是不是全新安装（不是，是在原有安装基础上重新构建的）。没有弹出提示，说明保存其实走的是"正常成功"的在线路径——只是没有把刚选的照片包含进去。这直接排除了上传和导航这两个方向，把问题指向了：照片选择器完成选择，和表单自身状态真正把新照片纳入进去，这两者之间存在一个时间差，而"保存"按钮在这个间隙里是可以被点击的。
5. **真正的修复。** 现在照片选择相关的函数（相册和拍照）会在其*整个*过程中——包括请求权限、打开原生选择器、以及把选中的照片写入表单状态——标记一个进行中的状态；在这个状态结束之前，保存按钮（以及保存函数内部的一道防御性检查）会一直保持禁用。这样无论前面几步各自耗时多久，都能彻底堵住这个空隙，而不必依赖"应该足够快"这种时间上的侥幸。同时也把上传确认逻辑里的 `HEAD` / `content-length` 检查，换成了直接查询 Supabase Storage 自己的 `list()` 接口——原来的检查依赖 CDN 对 `HEAD` 请求返回的响应头行为，而这一点其实并没有办法完全确认，很可能每次上传都在悄悄地判定失败。
6. **后续的体验优化。** 真正的问题解决之后，在网络较慢、多张照片确实需要一些时间上传时，保存按钮看起来仍然可能像是"卡住了"——因为当时只显示了一个加载动画。比起在每次保存时都弹一个需要手动关闭的提示框，更合适的做法是让按钮的加载状态直接说明情况：有新照片需要上传时显示"正在上传照片…"，否则显示"保存中…"，这样用户能明确知道应用正在工作，而不是卡死了。离线的情况在第 1 步就已经有清晰的"已离线保存"提示，所以不需要额外处理。
7. **最后一个缺口：同一个时间窗口，只是缺少视觉反馈。** 第 6 步之后，后续反馈进一步澄清了按钮"没反应"具体发生在什么时候：正是原生选择器关闭、到新照片真正显示在屏幕上之间的这段时间——也就是第 5 步已经处理为"安全"的那个窗口（保存按钮在这期间确实不会被触发），但当时并没有把这个状态"表现"出来。按钮在这段时间里外观完全正常，只是默默地忽略点击，跟卡死没有任何区别。修复方式：保存和取消按钮现在都会在这整个时间窗口内明确显示"正在添加照片…"的忙碌状态（复用第 5 步已有的 `pickingPhoto` 状态，不只用它控制 `disabled`，也用它驱动按钮外观），这样按钮要么可以点击，要么明确显示正忙——不会再出现"看起来能点、其实点不动"的空档。

## 调试记录：从相册选择视频完全没有反应

视频功能上线后不久发现的问题：用相机现场拍摄视频一切正常，但从相册里选一个*已有*的视频却像是什么都没发生——没有报错，没有视频缩略图，条目照样正常保存，只是没有把视频带进去。

1. **第一个猜测：文件太大。** 拍摄的视频有时长上限（60 秒），但从相册选择的视频没有这个限制，而 Supabase Storage 的存储桶如果不手动调高，默认会有一个比较小的体积上限。于是加了一道明确的客户端体积检查，并同步调高了存储桶的服务端上限（`supabase/006_video_size_limit.sql`），这样超出限制的文件会立刻给出清晰提示，而不是莫名其妙地失败。后来发现那条测试视频只有 6 秒，远远够不到任何一个上限，这个猜测被排除了——不过这道防护本身是真实有效、值得保留的。（这道检查的第一版把视频上限设成了 200MB，后来发现这个数字是错的：Supabase 免费套餐会强制执行一个硬性的**项目级 50MB 上限**，不管存储桶自己设的上限是多少。得知这一点后，把客户端检查改成了 45MB，也把拍摄的时长和画质设置一并调低，确保稳妥地控制在这个上限以内。）
2. **先区分是客户端问题还是服务端问题。** 确认了在点击保存之前，视频缩略图压根就没有出现在表单里——这说明问题根本不在上传或保存流程，而是选择器本身就没有把选中的视频返回给应用。
3. **一次关于构建缓存的误判。** 在选择器调用之后加的一个调试弹窗，即使做了彻底的重新安装也没有弹出来，一度看起来像是更底层的构建/缓存问题。后来在函数最开头（在任何其他代码执行之前）又加了第二个调试弹窗，这个弹窗正常弹出了，证明当时跑的确实是最新代码——真正的问题出在选择器调用本身的行为上，而不是缓存。经验：当一处改动看起来没生效时，应该先在函数最开头加一个诊断点，而不只是在怀疑的那一行附近加——这样能第一时间确认自己到底有没有在跑最新代码，避免绕远路去追一个根本不存在的缓存问题。
4. **真正的发现。** 一个打印选择器原始返回结果的调试弹窗显示 `canceled: true, count: 0`——尽管用户在选中视频后确实点了"Add"确认。这是 iOS 一个已知的怪癖：在照片选择器的多选模式下，点击视频缩略图有可能是打开预览，而不是勾选它的选中状态，于是在什么都没真正勾选的情况下点"Add"确认，返回的就是一个空的、被取消的结果。照片不存在这种歧义（点击必定是选中），这正是照片选择功能从没出过这个问题的原因。
5. **真正的修复。** 从相册选择视频现在改为单选模式，而不是多选。单选模式下，点击视频缩略图会直接选中并立刻关闭选择器，没有中间那个容易点错的确认步骤。拍摄视频（走相机）完全不受影响，因为它根本不经过这个选择器模式。视频本来通常也是一次添加一个，所以去掉多选并不会真的损失什么。

**下次需要留意的地方：** 如果以后再加新的上传类型或选择器流程（比如文档、音频），不要想当然地认为多选会和照片表现得一样——务必单独测试一遍。苹果的选择器在不同媒体类型上会有这种从 API 表面完全看不出来的怪癖。

## 调试记录："视频问题又出现了"——其实是另一个问题

后来又有一次反馈说，从相册选视频又不好使了——症状跟上面一模一样（没有视频缩略图，悄无声息地什么都没发生），一开始很容易被当成是那个已经修好的多选 bug又犯了。

6. **没有直接当成回归问题处理。** 在重新套用旧方案之前，先确认了之前的单选修复是不是还在、有没有正常工作——确认它一切正常。这说明这是一个披着相同症状外衣的、全新的问题。
7. **一次怀疑构建本身出了问题的弯路。** 在选择器调用之后加的调试弹窗没有弹出来，即使做了彻底的 Clean Build Folder 加重新安装也一样——这跟前面第 3 步遇到的"构建缓存"惊魂几乎一模一样。于是花时间去检查 Xcode 的 Run Script 构建阶段，还手动跑了一遍 `expo export:embed`，确认当前源码确实被打进了真实的 bundle 里（确实打进去了）。构建流程从始至终都没有问题。
8. **真正的缺口：只有 `try`，没有 `catch`。** 选择器调用被包在一个只有 `finally`、没有 `catch` 的 `try` 块里。选择器返回结果之后、调试弹窗触发之前，任何抛出的异常都被悄悄吞掉了——`finally` 依然会重置忙碌状态，所以"保存"按钮全程看起来完全正常，其他任何地方也都不会有任何提示。加上一个把原始错误弹出来的 `catch` 之后，立刻就看到了真正的原因：`PHPhotosErrorDomain error 3164`。
9. **真正的原因。** 这个错误是苹果 Photos 框架在导出一个尚未完整下载到设备上的视频时抛出的——只要开启了"优化 iPhone 存储空间"，相册里比较旧的视频就会被保留在 iCloud 上、按需下载，这种情况非常常见。经过实测验证：刚拍摄的视频（完全在本地）每次都能正常选取；只有那些被卸载到 iCloud 的旧视频才会失败。修复方式是专门捕获这个错误代码，给出清晰提示，告诉用户先在"照片"App 里打开这个视频（或者换到 Wi-Fi 下重试）把它下载下来，而不是像之前那样毫无反馈地悄悄失败。

**另外值得记住的一点：** 只有 `finally`、没有 `catch` 的 `try` 块，不只是"没处理错误"这么简单——它会让错误彻底**隐形**。`finally` 照样会把状态清理干净，所以表面上看不出任何卡顿的迹象，而异常本身则悄无声息地消失，既没有控制台输出，也不会崩溃。任何有用户可见结果的异步操作都应该带一个明确的 `catch`，哪怕只是简单地把原始错误弹出来——这点小小的保险，能省下这种排查好几个小时的弯路。

## 管理后台

一个轻量的静态网页应用（纯 HTML/CSS/JS，无需构建步骤），允许在 `profiles` 表中被标记为 `is_admin` 的账号登录后台，管理所有用户的记录——支持搜索、行内编辑、删除照片、删除条目。它直接访问同一个 Supabase 项目，权限完全通过行级安全策略（RLS）控制（见 `supabase/002_admin_panel.sql`），因此不需要额外的后端服务器。

已部署在 [worksite-diary.plos.xyz](https://worksite-diary.plos.xyz)，托管于 Cloudflare Worker。它的源码不属于本仓库——本仓库只包含授权它访问数据所需的 RLS 策略。
